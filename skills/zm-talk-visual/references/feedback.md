# 用户的反馈怎么记、怎么变成规则

这个 skill 是靠一条条反馈长出来的。用户看片说"好""不对""太普通"，是最值钱的信号。这份文件讲怎么把它留下来，让下一条片子做得更好。

## 记在哪

在用户自己的项目文件夹里（不是 skill 文件夹里）建一个 `反馈记录.md`，没有就新建。skill 文件夹会随更新被覆盖，记在里面会丢。

每条一行：

| 日期 | 片子 / 哪一段 | 用户的原话 | 背后的道理 | 下次要问自己的问题 |
|---|---|---|---|---|

- **原话照抄**，不改写。用户不用说清原因；"太普通"就记"太普通"。
- **背后的道理**是做的人自己想的：为什么会让他这么觉得？想不出就空着，不硬编。
- **下次要问自己的问题**是写给下一条片子的，比如"这一段除了人在说话，有没有东西在动？"

## 怎么变成规则

- 写成"原因 + 要问自己的问题"，**不写成固定的数字和位置**。"每 1.5 秒一个新画面"这种数字，换一条内容就不成立；"这句话的画面是不是它的证据"一直成立。
- 一次反馈只说明一条片子。同一类意见在两条以上的片子里出现，才算稳定的偏好，可以写进开工必读的位置。
- 和 skill 里的规则冲突时，以用户为准：照用户的做，并在反馈记录里写明哪条规则这次没守、为什么。

## 什么时候问"要不要存下来"

- 做完觉得哪个现做的镜头特别好：问用户要不要存进他的镜头库（照 `shot-library/own/cards/TEMPLATE.md` 写卡）。
- 用户对整条片子的样子很满意：问要不要存成一张风格卡（照 `references/style.md`《风格卡格式》）。
- 没有特别好的，就不问、不记。

## 被否掉的做法

用户明确否掉的做法，单独列一节"做过又被否的，别再做"，每条写清当时的原话和原因。这一节在每次开工时都要看一眼。
